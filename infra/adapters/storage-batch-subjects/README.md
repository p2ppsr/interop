# Prospective Go batch subjects and output observation

This additive layer reconstructs released `go-wallet-toolbox v0.191.4` through the immutable `storage-native-contracts` lock before applying the new patch. It does not change the executed 4.2 compatibility layer or its evidence.

`WalletServices.PostFromBEEF` previously called `ValidateSingleLeafTx` for the complete BEEF before iterating the explicitly requested transaction IDs. Consequently, an authenticated `signAction(sendWith: [...])` containing two independent held actions failed with `expected only one subject tx, but got 2`. The retained engineering observation is `out/transaction-coverage-reference/attempt-1794465655230/evidence/conformance/coverage-transactions.json`; it is not native qualification.

The replacement validation requires a full matching body for every requested subject and requires every graph leaf to be selected. Selected ancestors remain valid. Unknown subjects, omitted leaves and unrelated extra leaves fail before any provider invocation. All subjects complete hydration/EF preparation before submission starts. Caller ordering, duplicate-request behavior, shared proofs, and per-item provider results are retained. `ValidateSingleLeafTx` and its other callers remain unchanged. This layer does not claim that syntactically retained BUMPs independently prove mining; native parent verification still supplies that proof.

Run `node scripts/prepare-storage-batch-subjects-go.mjs` to reconstruct and verify every source/patch hash, run host, storage, service, validation, mapping and authenticated TypeScript RPC tests, and build `out/itcve-go-storage-batch-subjects`. The manifest binds its inputs, complete parent patch chain, generated host source and binary. Preparation copies the existing host command and injects exactly one additional route into its existing database/lifecycle. It does not modify that command or launch another service.

The new host exposes `GET /control/v2/native-output-snapshot?identityKey=<compressed public identity>` using the existing observer bearer token. Its explicit schema is `tpnil-native-output-snapshot@2.0.0`. The caller must bind both returned `identityKey` and `providerIdentityKey` to its controlled provider registry; the endpoint is not a public wallet API.

The snapshot reads every active output for that exact user in one database transaction, including pending rows, unspendable rows and names that public API validation would reject. It includes output/transaction IDs, outpoint, raw transaction, output index, satoshis, locking script, spendable flag, nullable basket/custom instructions and sorted active tags. Pending outputs explicitly have null outpoint/txid/rawTx; they are not represented as signed transactions. Every signed row must match its exact raw transaction ID, canonical complete bytes, output index, amount and locking script. Output, transaction and tag ownership must agree. Duplicate rows/outpoints/tags, missing signed raw bytes, malformed identities, ambiguous provider/user identities and exceeded budgets fail closed. Deleted outputs and deleted tag links are excluded explicitly.

Limits are 2,048 active outputs, 256 tags per output, 16 MiB per raw transaction, 2 MiB per locking script, 4 MiB per stored text value and 64 MiB aggregate payload fields. No private wallet state is read or mutated. The output table is the controlled storage provider's public transaction metadata. The observer cannot establish absence after its capture; final no-spend claims still require the complete verified shutdown submission graph.

Local tests and reference captures are engineering evidence only. Integration into a prospective profile and actual native execution are separate requirements.
