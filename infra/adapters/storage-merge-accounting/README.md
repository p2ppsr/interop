# Prospective merged-payment accounting correction

This immutable child of `storage-dust-accounting` fixes the net amount recorded when an existing transaction receives another wallet-payment internalization. Earlier layers and native evidence remain unchanged.

The Go provider already calculated the incremental value of newly managed outputs, but its existing-transaction branch discarded that delta. Internalizing two different 1,000-satoshi payment outputs therefore exposed both outputs while `listActions` still reported only 1,000. The correction adds the incremental managed value to the existing signed net amount within the same unit of work as output and label updates. Already managed outputs contribute zero, and recovery of a previously custom-basket output contributes its value once. Signed debits remain signed; the correction neither clamps nor takes absolute values.

The existing transaction is read under a database row lock. The write is additionally scoped to the authenticated user, transaction ID and previous amount; a stale or cross-user update fails. The no-change path verifies that the expected row still exists without depending on database affected-row conventions. Any subsequent output failure rolls back the amount update. The original read-only transaction lookup remains unchanged for other consumers.

Regression tests reproduce the original 1,000-versus-2,000 discrepancy through real SQLite storage and authenticated RPC, then cover repeat internalization, custom-output recovery, invalid later requests and cross-user access. Repository tests cover stale updates, idempotence, rollback and competing updates. The preparer runs these and the inherited storage, services, funding, HTTP, output-observer, mapping and validation suites.

Run `node scripts/prepare-storage-merge-accounting-go.mjs`. It reconstructs every pinned parent patch from Go wallet-toolbox v0.191.4 and emits `out/itcve-go-storage-merge-accounting` with manifest schema `tpnil-storage-merge-accounting-go-build@1.0.0`. The single host retains the batch layer's explicit v2 output observer. The manifest binds all patch ancestry, generated host source and build inputs. Admission is prospective and explicit; older native profiles cannot select this layer.

The source-stable 122-call TypeScript-to-Go engineering reference observed 20 PASS, one FAIL and one BLOCKED. Incremental credit, batch submission and all no-send checks passed. The remaining failure was separately traced to the reference TypeScript 2.13 client's conflicting-proof canonicalization, and the blocked result is an unresolved inactive-remittance interpretation. These are engineering observations, not native wallet qualification. Failed and passing source-bound evidence is retained under `out/storage-merge-accounting-review` for append-only publication.
