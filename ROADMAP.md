# Roadmap and acceptance gates

## Gate 0 — ratify the foundation

The charter, governance, licensing policy, initial candidates, and determinism model establish the foundation. This gate requires adopted technical scopes, resolved initial clause-level interpretations, and passing core integrity, replay, incomplete-evidence, and journal-history checks. Third-party contributions and artifacts require their respective acceptance records. Public release follows a separate steward decision.

## Gate 1 — qualify the common ITCVE

Build a fully offline Linux/amd64 regtest closure from pinned Teranode, Arcade, Merkle Service, ChainTracks, storage, overlay, and content dependencies. Provision an immutable OS and service image catalog; verify chain identity, maturity, deterministic funding, transport capture, external network denial, reset, and teardown. Deployment definitions must resolve to exact artifacts and a complete dependency inventory. Build cluster images on amd64 CI or appropriate infrastructure.

## Gate 2 — first wallet/application pair

The nominated todo-ts source has a compiled candidate tarball with archive/file-tree digests and two matching local builds. Next qualify its reproducible build environment and complete artifact admission. Admit canonical BSV Desktop release binaries only after they demonstrate the uniform regtest lifecycle. If a change is needed, propose upstream support and wait for a new canonical release; a local patch is a different SUT. Qualify one exact desktop/browser pair, then expand to the declared matrix.

Execute independent ToDo create/list/reload/decrypt/redeem/spendability assertions and record two clean repetitions. Validate returned transaction bytes, basket state, and chain state independently of UI markers. The acceptance evidence comprises executed application, wallet, and chain observations.

## Gate 3 — isolated interoperability boundaries

Freeze overlay and storage HTTP contracts, extract reviewed method inventories, provide independent canonical state projections and fixtures, and exercise TS/Go cross-implementation matrices. Include transaction admission, lookup, bounded synchronization, restart/resume, idempotence, pending/proven/conflicted state, portability, and no-data-loss checks. Publish every matrix cell and omission.

## Gate 4 — integrated scenario and native matrix

Run onboarding and ToDo from locally mined coins across the full stack. Add a pinned message-board application that writes a GlobalKVStore PushDrop payload containing an LCH-controlled UHRP image reference; independently resolve and validate bytes, rights/payment receipts, keys, and rendering, then exercise the CHIRP variant. Qualify device-specific IPA, APK/AAB, Windows, macOS, Linux, Chrome, Safari, Brave, and mobile wallet-browser profiles. Safari qualification requires Safari in a licensed Apple environment.

## Gate 5 — independent laboratory reproduction

A separately administered operator reconstructs the closed environment from the public record, lawfully obtains the exact binaries, repeats the matrix, and independently verifies journals and oracle outputs. Demonstrate recovery, archival retrieval, disputed result handling, and quorum/recusal before any certification launch.

Each gate requires recorded evidence and an assigned owner. No calendar deadline substitutes for meeting a gate. Future testing may add consensus/network policies, additional languages, hardware wallets, alternative storage engines, and new ISIs without changing historical claims.
