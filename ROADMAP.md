# Roadmap and acceptance gates

## Gate 0 — ratify the foundation

The charter, governance, licensing policy, initial candidates, and determinism model establish the foundation. This gate requires adopted technical scopes, resolved initial clause-level interpretations, and passing core integrity, replay, incomplete-evidence, and journal-history checks. Third-party contributions and artifacts require their respective acceptance records. Public release follows a separate steward decision.

## Gate 1 — establish the production-wallet intake boundary

The hybrid execution architecture is adopted under [ISI-4 decision 0003](programs/ISI-4/decisions/0003-hybrid-laboratory.md). The portable application-serving lane is executable and produces infrastructure-only evidence. Native execution remains blocked under [decision 0002](programs/ISI-4/decisions/0002-native-infrastructure.md) until the disposable macOS runner is provisioned, qualified, and documented.

Apply [production SUT intake](docs/intake.md) to the unchanged release. Verify artifact identity and signatures, ordinary mainnet settings, local and remote storage modes, all service dependencies, and configuration effects. Source observations guide the inventory; native observations establish actual routing and behavior. The first BSV Desktop 2.8.5 intake is blocked pending runtime evidence.

Provision a clean native guest and qualified automation. Resolve the required service routes through ordinary supported configuration. Pin the complete controlled-service closure and mainnet-format fixture model. The initial profile permits no public-mainnet broadcast or funds. Unresolved mandatory dependencies block the affected vectors while other observable behavior remains eligible for separately scoped evaluation.

## Gate 2 — execute the first ToDo sequence

Admit the compiled todo-ts artifact and canonical wallet configuration under ISI-4 1.0.0. Serve the application at the canonical origin. Implement independent create/list/reload/decrypt/redeem assertions and record two clean repetitions with retained raw evidence. Validate transaction bytes, scripts, amounts, basket state, encryption context, and declared service-state transitions independently of UI markers.

The initial demonstration covers V001–V004. Complete BRC-100 coverage and public-mainnet acceptance have separate evidence requirements. Wallet regtest support and special test builds are not prerequisites for this profile.

## Gate 3 — isolated interoperability boundaries

Freeze overlay and storage HTTP contracts, extract reviewed method inventories, provide independent canonical state projections and fixtures, and exercise TS/Go cross-implementation matrices. Include transaction admission, lookup, bounded synchronization, restart/resume, idempotence, pending/proven/conflicted state, portability, and no-data-loss checks. Publish every matrix cell and omission.

## Gate 4 — integrated scenario and native matrix

Qualify the full-stack profile, including its pinned Teranode/Arcade/Merkle/ChainTracks closure and declared funding model. Connect its integration findings to the production-wallet profile with explicit configuration and dependency differences. Add a pinned message-board application that writes a GlobalKVStore PushDrop payload containing an LCH-controlled UHRP image reference; independently resolve and validate bytes, rights/payment receipts, keys, and rendering, then exercise the CHIRP variant. Qualify device-specific IPA, APK/AAB, Windows, macOS, Linux, Chrome, Safari, Brave, and mobile wallet-browser profiles. Safari qualification requires Safari in a licensed Apple environment.

## Gate 5 — independent laboratory reproduction

A separately administered operator reconstructs the closed environment from the public record, lawfully obtains the exact binaries, repeats the matrix, and independently verifies journals and oracle outputs. Demonstrate recovery, archival retrieval, disputed result handling, and quorum/recusal before any certification launch.

Each gate requires recorded evidence and an assigned owner. No calendar deadline substitutes for meeting a gate. Future testing may add consensus/network policies, additional languages, hardware wallets, alternative storage engines, and new ISIs without changing historical claims.
